## 2. Cómo ponerlo a andar

### Requisitos

- **Node.js 20.9 o superior** (Next.js 16 no corre con versiones anteriores)
- **PostgreSQL 17** con *Command Line Tools* instalado
- **Git**

### Pasos

```bash
git fetch origin
git checkout feature/us01-autenticacion
cd pos-app
npm install
```

Crear la base de datos (una sola vez, cada quien en su máquina):

```bash
psql -U postgres -c "CREATE DATABASE pos_hibrido;"
psql -U postgres -d pos_hibrido -f ../sql/01_usuarios.sql
```

Crear el archivo `pos-app/.env.local` con estas dos líneas:

```
DATABASE_URL=postgresql://postgres:SU_CONTRASEÑA@localhost:5432/pos_hibrido
AUTH_SECRET=una_cadena_larga_y_aleatoria
```

Para generar el `AUTH_SECRET`:

```bash
node -e 'console.log(require("crypto").randomBytes(32).toString("hex"))'
```

Arrancar:

```bash
npm run dev
```

### ⚠️ Advertencias

- **`.env.local` no se sube al repositorio** (está en el `.gitignore`). Cada quien crea el suyo con su propia contraseña de Postgres.
- **Si su contraseña de Postgres tiene `@`, `:`, `/`, `#`, `?` o `%`, el `DATABASE_URL` se rompe.** Esos caracteres son separadores dentro de una URL. Usen una contraseña de solo letras y números, o cámbienla con:
```bash
  psql -U postgres -c "ALTER USER postgres WITH PASSWORD 'nueva_clave';"
```
  (Ver la sección 8: hay una propuesta para eliminar este problema de raíz.)
- **Si editan el `.env.local` con el servidor corriendo, hay que reiniciarlo** (`Ctrl + C` y `npm run dev` otra vez). Las variables de entorno se leen solo al arrancar.

## 4. Por qué la sesión se maneja con una cookie firmada

Esta parte no estaba en la historia original. La agrego porque sin ella el login queda a medias: validar las credenciales sirve de poco si el sistema olvida quién eres en la siguiente página.

### El problema

HTTP no tiene memoria. Cada petición al servidor llega sin saber nada de las anteriores. Si iniciaste sesión y luego entras al catálogo, para el servidor eres un desconocido otra vez. Hace falta algo que viaje en cada petición diciendo quién eres.

### Por qué una cookie y no `localStorage`

`localStorage` es el otro lugar donde se suele guardar esto. Lo descarté porque **el JavaScript de la página puede leerlo**. Si alguien logra inyectar un script en el sitio (un ataque XSS), puede leer el token y suplantar al usuario.

Una cookie marcada como **`httpOnly`** no la puede leer ningún JavaScript, ni el propio de la página. El navegador la guarda y la envía sola en cada petición, pero el código nunca la ve. Es la diferencia entre guardar la llave en el bolsillo o dejarla pegada en la puerta.

### Por qué va firmada

La cookie vive en el navegador del usuario, que es su computador. Puede abrir las herramientas de desarrollador y editarla. Si la cookie dijera simplemente:

```
sesion=maria@correo.com|CLIENTE
```

cualquiera la cambiaría a `|ADMIN` y entraría al panel de administración.

Por eso el contenido se **firma** con el `AUTH_SECRET` usando JWT (*JSON Web Token*). La cookie queda así:

```
eyJhbGciOiJIUzI1NiJ9.eyJpZF91c3VhcmlvIjoiMSJ9.dQ7x...
```

Tres partes: cabecera, datos y **firma**. Si alguien cambia una sola letra de los datos, la firma deja de coincidir y `jwtVerify` rechaza el token. Y no puede generar una firma válida nueva porque no tiene el `AUTH_SECRET`, que solo existe en el servidor.

### Lo que esto NO hace

Para no vender más de lo que es:

- **No cifra.** Los datos del token están codificados en Base64, no encriptados: se pueden leer. Por eso ahí solo van `id_usuario`, `correo`, `nombre` y `tipo_usuario` — nada sensible, y nunca la contraseña.
- **No se puede revocar antes de que expire.** Si a alguien le quitan el rol de administrador, su token sigue siendo válido hasta que caduque (7 días). Con una tabla de sesiones sí se podría cerrar al instante.

### Por qué `jose` y no `jsonwebtoken`

`jsonwebtoken` es la librería más conocida, pero usa el módulo `crypto` de Node. En Next.js hay partes que no corren sobre Node sino sobre un entorno más limitado — en concreto el archivo `proxy.ts`, que es donde se hará la protección de rutas (impedir que un cliente entre a `/admin`).

`jose` usa **Web Crypto**, que funciona en ambos entornos. Así, cuando se implemente la protección de rutas, este mismo código de sesión sirve sin reescribir nada.

### Alternativa que se consideró

Guardar las sesiones en una tabla de la base de datos, con un token aleatorio por usuario. Ventaja real: permite cerrar una sesión al instante. Se descartó porque exige una tabla que no está en el MER/MR, y porque obliga a una consulta a la base en **cada** petición. Para el alcance de este proyecto, la cookie firmada es suficiente y más simple.

### Sobre los "asteriscos" de la contraseña

La historia pide que *"la contraseña se muestra oculta con asteriscos"*. Se implementó con `type="password"`, que es la forma estándar. **Chrome y Edge dibujan puntos (••••), no asteriscos** — eso lo decide el navegador y el sistema operativo, no el código. Forzar asteriscos literales exige un truco que rompe el cursor y el autocompletado. Se cumple el propósito (la contraseña está oculta) aunque el símbolo sea distinto.

## 6. Contrato de la API — para el resto del equipo

Todos los endpoints reciben y devuelven JSON.

### `POST /api/auth/registro`

```json
{ "nombre": "...", "correo": "...", "cedula": "...", "contrasena": "..." }
```

| Código | Significado |
|---|---|
| `201` | Creado. Devuelve `{ usuario }` y deja la sesión abierta. |
| `400` | Alguna validación falló. Devuelve `{ error }` con el mensaje. |
| `409` | El correo o la cédula ya existen. |
| `500` | Error del servidor. El detalle queda en el log, no se envía al navegador. |

### `POST /api/auth/login`

```json
{ "correo": "...", "contrasena": "..." }
```

| Código | Significado |
|---|---|
| `200` | Correcto. Devuelve `{ usuario }` y abre la sesión. |
| `400` | Faltan campos. |
| `401` | Credenciales incorrectas. |

### `POST /api/auth/logout`

Sin cuerpo. Devuelve `{ "ok": true }` y borra la cookie.

### `GET /api/auth/sesion`

Devuelve `{ "usuario": { id_usuario, correo, nombre, tipo_usuario } }` o `{ "usuario": null }`.

### Para saber quién está conectado

Desde una **página de cliente** (con `"use client"`):

```ts
const respuesta = await fetch("/api/auth/sesion");
const { usuario } = await respuesta.json();
```

```ts
import { obtenerSesion } from "@/lib/sesion";
```

## 8. Pendientes que dependen de Daniel

Cuatro puntos donde el MR y esta historia no encajan del todo. **Ninguno bloquea el trabajo actual**, pero hay que resolverlos antes de integrar.

### 8.1 `cedula` es `NOT NULL`

El registro del e-commerce, según lo hablado, iba a pedir solo correo y contraseña. Pero en el MR la cédula es obligatoria y única, así que no se puede insertar sin ella.

**Solución actual:** se pide la cédula en el formulario.
**Alternativa:** volverla `NULL` en el modelo y quitar el campo del formulario.
**Decide:** Daniel + el equipo.

### 8.2 `contrasena` guarda un hash, no una contraseña

Un hash de bcrypt son 60 caracteres. Aquí se declaró `VARCHAR(255)`. **Si en el script oficial quedó más corta, va a fallar al insertar.**

**Propuesta:** renombrarla `contrasena_hash` para que quede explícito que ahí nunca va texto plano.

### 8.3 Falta la columna `activo`

La US_02 dice textualmente *"el administrador puede consultar, modificar y **desactivar** usuarios"*. En el MR no hay ninguna columna que permita eso.

**Propuesta:** `activo BOOLEAN NOT NULL DEFAULT TRUE`. Cuando exista, hay que añadir la verificación en `api/auth/login/route.ts` para impedir que un usuario desactivado inicie sesión.

### 8.4 Valores exactos de `tipo_usuario`

Se asumió `'ADMIN'`, `'VENDEDOR'`, `'CLIENTE'` en mayúscula, según el MER y el `types.ts` de la rama `test`. **Confirmar.**

### 8.5 (Para el equipo) ¿Con qué contraseña entra un cliente registrado por el cajero?

La US_03 dice que el cajero registra clientes con nombre y correo, y que ese correo *"debe utilizarse como identificador de acceso del cliente en la página virtual"*. Pero no dice de dónde sale su contraseña. Opciones: se le genera una temporal, o se le envía un enlace para que la cree. **Hay que decidirlo**, porque afecta tanto a la US_03 como a este login.

### 8.6 Propuesta técnica para `lib/db.ts`

El problema de los caracteres especiales de la sección 2 existe solo porque las credenciales van dentro de una URL, donde `@` y `:` son separadores.

La librería `pg` acepta las variables por separado. Si el `.env.local` fuera así:

```
PGHOST=localhost
PGPORT=5432
PGUSER=postgres
PGPASSWORD=cualquier@cosa#rara
PGDATABASE=pos_hibrido
```

y `db.ts` así:

```ts
export const pool = globalForPg.pgPool ?? new Pool()
```

el problema **desaparece por completo**: no hay que advertir nada ni validar nada, porque el error ya no puede ocurrir. Son dos líneas y encaja con las observaciones de la propia US_07 (*"se recomienda utilizar variables de entorno"*).

**No se cambió aquí** porque `lib/db.ts` es de la US_07 y le corresponde a Daniel.

### 8.7 El MER y el MR no coinciden entre sí

El MR incluye `Proveedor`, `SolicitudProveedor`, `DetalleVenta` y `DetalleCarrito`, que no aparecen en el MER. Conviene alinearlos antes de la entrega.
